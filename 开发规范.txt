# SidebarMemo 开发规范：必须严格遵守

你正在修改一个 Tauri 2 桌面应用：Vue 3 + TypeScript 前端，Rust 后端，SQLite 数据库。用户是小白，不能接受“能跑但埋 bug”的修改。你的任务不是只完成表面功能，而是保证现有功能不被破坏。
如果发现中文乱码：
1. UI 文案、title、placeholder、注释中的乱码，必须改成正常简体中文。
2. 不允许删除功能代码来“处理乱码”。
3. 不允许修改 IPC 命令名、数据库字段名、配置 key，除非确认没有依赖并说明原因。
4. 修复乱码后必须运行 `npx vue-tsc --noEmit` 和 `npm run build`。

## 一、开始修改前必须做的事

1. 先阅读相关代码，不允许凭空猜测。
2. 修改前必须说明：
   - 这次会改哪些文件
   - 为什么要改这些文件
   - 是否涉及数据库、设置文件、IPC、窗口行为、快捷键、托盘、UI 文案
3. 如果需求不明确，必须先提出问题，不允许擅自设计会影响数据或用户习惯的行为。
4. 不允许大范围重构。只改和本次需求直接相关的代码。
5. 不允许删除现有功能，除非用户明确要求。

## 二、项目结构约束

前端代码位置：

- 页面级组件放在 `src/views/`
- 可复用组件放在 `src/components/`
- 共享状态和业务调用放在 `src/composables/`
- `useMemos.ts` 和 `useSettings.ts` 是模块级单例状态，不允许改成每个组件单独创建状态

后端代码位置：

- Tauri 启动、IPC 命令、托盘、快捷键、窗口逻辑在 `src-tauri/src/lib.rs`
- SQLite 存储逻辑在 `src-tauri/src/db.rs`
- 不要把数据库 SQL 写到前端
- 不要把复杂业务逻辑塞进 Vue 模板里

配置文件：

- 新增 Tauri 插件、窗口能力、系统权限时，必须检查 `src-tauri/capabilities/default.json`
- 新增 npm 依赖前必须说明原因，能不用新依赖就不用
- 不要随意改 `vite.config.ts`、`tauri.conf.json`、`Cargo.toml`

## 三、IPC 命令规范

如果新增前端调用 Rust 的能力，必须完整检查以下链路：

1. 在 `src-tauri/src/lib.rs` 添加 `#[tauri::command]`
2. 命令返回值必须是 `Result<T, String>`，除非确实不需要返回错误
3. 命令必须加入 `tauri::generate_handler![...]`
4. 前端必须通过 `@tauri-apps/api/core` 的 `invoke` 调用
5. 前端必须写准确的 TypeScript 返回类型
6. 前端调用必须 `try/catch`，错误要通过现有 toast 或现有错误方式提示
7. 如果涉及权限或插件能力，必须检查并更新 `src-tauri/capabilities/default.json`

不允许出现：
- Rust 命令写了但没注册
- 前端 `invoke` 的命令名和 Rust 不一致
- 前端类型和 Rust 返回结构不一致
- 出错只 `console.log`，用户无感知

## 四、数据和数据库规范

数据库只允许在 `src-tauri/src/db.rs` 修改。

如果新增字段，必须：

1. 修改 Rust `Memo` 结构体
2. 修改数据库建表 SQL
3. 添加迁移到 `MIGRATIONS`
4. 保证老用户已有数据库可以升级
5. 修改所有 `SELECT` 字段列表
6. 修改 `row_to_memo`
7. 修改新增/更新/查询逻辑
8. 同步修改前端 `Memo` TypeScript 接口
9. 说明老数据默认值是什么

禁止：
- 直接删表重建
- 破坏现有用户数据
- 只改新安装场景，不考虑已有数据库
- 使用字符串拼接 SQL，必须使用 `params!`

## 五、设置项规范

设置存储在 `{config_dir}/sidebar-memo/settings.json`。

如果新增设置项，必须：

1. 修改 Rust `Settings`
2. 给字段添加合理默认值
3. 如果是新增字段，必须考虑旧 settings.json 没有该字段的情况，使用 `#[serde(default)]`
4. 修改前端 `Settings` interface
5. 修改 `useSettings.ts`
6. 确保保存一个设置项时不会丢失其他设置项
7. 如果设置影响窗口、快捷键、主题等，必须立即应用并持久化

特别注意：前端 `Settings` 类型必须和 Rust `Settings` 保持同步。

## 六、前端状态规范

1. `useMemos.ts`、`useSettings.ts` 的状态是共享单例，不允许改成局部状态。
2. 修改 memo 后，必须同时考虑：
   - 后端数据库是否成功
   - 前端列表是否同步更新
   - 垃圾桶列表是否同步
   - 置顶列表和普通列表是否同步
   - 搜索和日期筛选是否仍正确
3. 不允许为了刷新简单粗暴重载整个页面。
4. 乐观更新必须在后端成功后进行，或者失败时回滚。

## 七、UI 和中文规范

1. UI 文案和注释使用简体中文。
2. 不允许继续引入乱码。
3. 修改 `.vue` 文件时必须保证文件保持 UTF-8。
4. 如果发现已有中文乱码：
   - 不要扩大乱码范围
   - 本次需求涉及到的乱码文案必须顺手修复为正常中文
5. 按钮必须有明确的 `title` 或可理解的文字/图标。
6. 不要随意改变整体布局、颜色体系、窗口大小、拖拽区域和侧边栏结构。
7. 小功能优先融入现有界面，不要做成新的大页面，除非用户明确要求。

## 八、窗口、快捷键、托盘相关规范

这类功能风险较高，修改前必须特别说明影响范围。

涉及以下内容时必须小心：

- 全局快捷键
- 窗口显示/隐藏
- 置顶
- 最小化
- 托盘
- 窗口位置保存
- 窗口尺寸调整

要求：

1. 不允许破坏 Alt/自定义快捷键唤出窗口的行为。
2. 不允许让关闭按钮直接退出程序，除非用户明确要求。
3. 修改窗口位置/尺寸逻辑时，必须保留越界检测，避免窗口跑到屏幕外。
4. 修改快捷键解析时，必须保持已有格式兼容，如 `Alt+Space`、`Ctrl+Shift+A`。

## 九、验证规范

每次修改完成后，必须至少运行：

```bash
npx vue-tsc --noEmit
如果改动涉及构建、Tauri 配置、依赖、Rust、数据库、IPC，必须再运行：
npm run build
如果无法运行，必须明确告诉用户原因。
最终回复必须包含：
1.改了哪些文件
2.实现了什么
3.验证命令是否通过
4.有哪些风险或需要用户手动确认的地方

禁止：
大范围重构
顺手美化无关代码
删除用户数据
修改 node_modules、dist、src-tauri/target
直接改构建产物
引入未说明的新依赖
忽略 TypeScript 错误
用 any 绕过类型，除非必须，并说明原因
前端和后端字段名不一致
新增功能只做 UI，不接真实数据
新增数据库字段但不写迁移
新增 IPC 命令但不注册
修改后不验证

给出简短修改计划
小范围修改
自查前后端类型、IPC、数据库、设置项
运行验证命令
修复验证发现的问题
最终汇报
